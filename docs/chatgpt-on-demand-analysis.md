# ChatGPTの依頼時に使うデータと分析契約

## 目的と担当分担

このリポジトリは、ブラックフライデーの購入に向けた**継続監視・証拠データの収集・履歴保存・データ品質検査**を担当する。GitHub Actionsのランキングやレポートは中間的な診断情報とデータ索引であり、ユーザーへ提示する最終的な推薦順位ではない。

ユーザーがChatGPTで「ランキングを出して」「今買うべきか詳しく分析して」などと依頼した時点で、ChatGPTが最新データを読み、必要な外部確認も行い、最終結果を組み立てる。

## 正本として先に読むデータ

|目的|ファイル|読み方|
|---|---|---|
|BTOデスクトップ・ノートPCの最新観測| `data/current_latest.json` |生成時刻、各候補の価格、型番一致、在庫、取得状態、観測時刻を確認する|
|BTOなどの価格・在庫変化履歴| `data/change_events.jsonl` |新旧の変化イベントを確認する。欠けている期間を値下がりなしと推測しない|
|自作パーツの最新市場参考値| `data/build_component_prices.json` |部品SKU・価格検証状態・PIT・価格ソース役割・在庫診断を確認する|
|自作パーツの時系列証拠| `data/build_component_observations.jsonl` |部品ごとの過去観測を確認し、BF前参考値とBF期間中観測を分離する|
|周辺機器の最新観測| `data/peripheral_prices.json` |モニター、スピーカー、キーボード、マウスなどを別々に確認する|
|周辺機器の価格・在庫履歴| `data/peripheral_change_events.jsonl` |商品の変化履歴と観測範囲を確認する|
|公式2026年セール日程の証拠| `data/official_campaign_dates_status.json` |店舗ごとに確認状態、公式URL、期間、取得失敗を読む。暫定監視窓は公式期間の代わりにならない|
|監視窓内の厳格な価格観測| `data/buy_now_observations.jsonl` |有効な観測だけでなく、観測件数と窓の開始・終了時刻も確認する|
|手動整理された価格の基準点| `data/historical_public.csv`, `config/history_anchors.json`, `config/public_baselines.json` |根拠URL・観測日を確認し、単発記事や古い参照価格を全期間最安とみなさない|
|監視対象の完全性| `data/watchlist.json`, `config/candidate_catalog.json`, `config/build_components.json`, `config/targets.json` |カタログ・監視URL・予算・商品型番・対象範囲が食い違っていないか確認する|
|自動生成されたスコアと概要| `data/decision_rankings.json`, `data/buy_now_decision.json`, `data/self_build_plan.json`, `data/timing_analysis.json`, `data/scenario_analysis.json`, `data/reports/*.md` |内部診断や検索用の索引として参照するだけ。これだけで最終順位を決定しない|

## ChatGPTが最終ランキングを作る手順

1. **依頼条件を固定する。** その会話内でユーザーが最後に指定した総予算、PC本体と周辺機器の対象、ゲーム、AI・Pythonなどの用途、必須容量を優先する。古い設定ファイルやREADMEの予算へ無断で戻さない。
2. **データ鮮度を監査する。** 各ファイルの生成時刻、個別観測時刻、記録件数、最新イベント、取得成功率、SKU不一致、未知在庫、失敗ホストを調べる。取得されていない価格は0円にしない。
3. **購入判断に関わる情報を再確認する。** 公式ストアや販売店の商品ページで正確な型番、販売元、決済前価格、在庫、送料、適用できるクーポン、出荷条件、公式2026年セール期間を確認する。確認できなければ未確認とする。
4. **価格の種類を分離する。** 「BF購入目標価格」は希望する購入水準、「BF前の参考価格」は期間前の値、「監視で実際に観測した価格」は取得時点の証拠、「公式キャンペーン期間内の確認済み価格」は公式期間と紐付いた観測、「最終決済額」はカートで確認された現金支払額として別々に扱う。ポイントや未適用クーポンは、現金値引きとして数えない。
5. **同じ条件で予算を計算する。** 自作は全パーツ、Windows、送料、小物、必要ケーブルを含める。CPUのメーカーサポートリストと必要BIOS、実際の出荷/搭載BIOS、選択メモリ型番のマザーボードQVL、GPU寸法・スロット厚・補助電源を個別に確認する。未確認はREVIEWとして表示し、ソケットや容量が一致するだけで互換性PASSにしない。BTOはRAM 32GB以上・SSD 1TB以上に設定した完成構成の最終価格を使う。周辺機器は各カテゴリ1候補ずつとし、PC＋周辺機器の合計から予算内の可否を計算する。 価格が正確な商品ページから新鮮な観測として検証できていても在庫がunknownの場合は、費用試算には目標額と確認済み掲載価格の高い方を使い、在庫・購入ゲートは未解決のままにする。価格そのものが未確認の場合に限り目標額を暫定リザーブとして使う。この費用試算は最終カート価格を保証しない。
6. **各ランキングを分けて提示する。** 全体構成ランキング、CPU・GPU・メモリ・SSDなどの部品候補、メインモニター、サブモニター、スピーカー、キーボード、マウスなどのカテゴリ別順位、RTX 5070 Tiなどの大穴を必要に応じて個別に示す。各候補の理由・画像/商品リンク・予算内総額・未確認条件・在庫切れリスク・「今買う/待つ」を示す。
7. **不確実性を残す。** 監視スコアは購入優先度の補助であり、値下がり確率ではない。過去のセール事例が少なければ、値下がり幅や確率を数値で作らない。商品ページの取得失敗は売り切れとは扱わない。購入条件が未達なら買い時候補として残しても購入許可を出さない。

## ランキング依頼時の必須出力契約

現時点の構成計画の中心目標は**総額約400,000円**、周辺機器目標69,800円、PC本体計画枠330,200円です。ただし、ユーザーが会話で新しい予算・対象・用途を指定した場合はその最新条件を優先します。40万円は比較の中心目標であって、RTX 5070 Tiなどの大穴候補をランキングから除外する条件ではありません。目標超過候補は超過額・必要な値下げ額・成立条件を明示し、購入許可と候補としての比較を分けます。

**ランキングを依頼されたら、必ず最初にデータの状態を報告します。** 確認時刻（JST）、各正本ファイルの生成時刻、対象候補数、現在価格・在庫の確認件数と未確認件数、公式2026年BF日程を確認できた店舗数、失敗/鮮度切れ/型番不一致の数を示します。データが揃っていない項目を「完全」と表現せず、現時点の証拠で確定できる順位と暫定順位を分けます。

最低限、次を別のランキングとして作成します。

1. **PC全体構成**：自作を主方式にし、RTX 5070 12GB本命、RTX 5060 Ti 16GBのVRAM重視案、RTX 5070 Ti 16GB等の大穴を含める。候補の追加発見も行う。全構成で出荷時RAM 32GB以上・SSD 1TB以上を満たす。PC部品、正規Windows、送料、小物、必要ケーブル、周辺機器を含む総額と目標差額を計算し、互換性や最終見積が未確認なら明記する。
2. **PCパーツカテゴリ**：CPU、GPU、マザーボード、メモリ、SSD、電源、ケース、CPUクーラー、OS。登録済み候補が少ないカテゴリも明示し、メーカー仕様・販売店ページに基づく代替候補を補う。メモリは正確な型番・容量・モジュール構成・QVL/BIOSを確認し、購入後増設を前提にしない。
3. **周辺機器カテゴリ**：メインモニター、サブモニター、スピーカー、キーボード、マウス、マウスパッド、電源タップ、ケーブル。ヘッドセットは追加しない。全候補を同時購入した総額にせず、各カテゴリから選んだ1品だけを総額へ加算する。
4. **買い時・売り切れリスク**：「今買う」「BFまで待つ」「在庫リスクを見て条件付きで早く買う」「大穴として監視」を分ける。値下げ目標への距離、価格履歴内の安値、公式セール期間内の実測値、売り切れリスクは別指標として扱う。根拠の薄い値下がり確率を作らない。

各商品行には、順位、カテゴリ、正式商品名と型番、現在確認価格とその種類、BF購入目標、在庫状態、確認時刻、販売ページへのリンク、取得可能な公式/販売店の商品画像、性能・コスパの根拠、総額への影響、互換性・販売条件リスク、「今買う/待つ」判断条件を含めます。画像または直接販売ページが確認できない場合は推測で補完せず未確認と書きます。

価格ラベルは厳密に分けます。

- **BF購入目標価格**：狙う希望額。予測でも実売でもない。
- **BF前の参考価格**：BF公式期間外の参考観測。
- **現時点で確認できた参考価格**：確認元・型番・取得時刻・在庫状態を伴う現在観測。
- **BF期間内の確認済み価格**：販売店の公式2026年開催期間と取得時刻が一致し、正確な商品・販売元・価格条件・在庫・PITを検証した観測。
- **最終決済額**：販売店の最終カートで送料や適用条件まで確認できた現金支払額。

取得エラー・検索スニペット・古い価格・型番不一致は、在庫切れやBF実売へ読み替えません。ポイントは現金値引きとして二重計上せず、クーポンも適用条件が決済で確認できるまで控除しません。構成総額は選択された商品の集合から再計算し、代替パーツやカテゴリ別2位以下を二重計上しません。生成済みランキング・スコアはデータ索引と診断用であり、その数字を無検証で最終順位へ転記しません。

## データの完全性の測り方

「完全なデータ」とは、実在しない全店舗情報を埋めることではなく、対象範囲を広く保ち、取得に成功した証拠を積み上げ、欠測・古さ・識別不一致・通信エラー・在庫不明を隠さず管理することを指す。

- 商品モデル/SKU、販売店、取得URL、価格の種類、税込/送料条件が識別できる情報、在庫、`retrieval_time`、`available_at`、公式キャンペーン期間、PIT検証状態を可能な限り保存する。
- 利用可能性の根拠が不明な場合は `unknown` を保持する。値段が検索スニペットだけの場合は、直接取得・SKU一致の確認済み価格へ昇格させない。
- `available_at <= retrieval_time <= prediction_time` を守る。時間が欠けたデータは予測時点以前に利用可能だったと仮定しない。
- 履歴イベントは上書きで失わず追記し、スナップショットとレポートの生成時刻を確認する。
- 取得範囲、エラー、対象未登録、更新遅延を見える化し、既存のGitHub Actionsテスト・healthcheck・validateを通して監視基盤自体も点検する。

## 依頼例

> 監視リポジトリの最新データと現在の販売ページを確認して、総額40万円のブラックフライデー構成ランキングを出して。大穴も含め、PC本体・各パーツ・周辺機器カテゴリを別々に順位付けし、画像・購入リンク・確認済み価格と目標価格の区別・売り切れリスク・今買うか待つかを示して。

この例は形式の説明であり、予算は実際の依頼に書かれた最新条件を使う。
