- 監視対象カタログ、watchlist、最新観測データのID・型番・URLが整合し、監視対象の欠落・URL差し替わりが自動検出される。

- 履歴は追記型で残し、過去価格の上書きや別型番の価格引継ぎを禁止する。時刻・同一SKU・価格の妥当性・PIT（prediction/decision timeより後に判明した情報を当時の情報に混ぜない）を検証する。
- 直接取得不能時は、許可された別の公式/小売商品ページを順次試す。検索スニペットは参考専用として隔離し、購入判定・値下がり幅・価格平均の基礎には使わない。

### B. 監視運用・回復

- 通常監視は原則15分間隔、公式BF期間が確認できた対象・監視窓では優先度を上げて約5分間隔を目指す。ただしGitHubのscheduleは実行時刻を保証しないため、設定ではなく実測で可用性を評価する。
- 通常期にデータが45分以上古い、優先監視期間に20分以上古い場合はALERTを出し、watchdogが復旧処理を試みた事実を履歴で検証できる。
- 監視の正常性は「最新の成功」だけで判定しない。予定時刻、実行開始時刻、完了時刻、スキップ理由、復旧実行、再失敗を一覧で検査する。連続稼働を主張するには、一定期間の実測成功率と欠落時間が必要。
- GitHub Actionsが起動しない時間帯をコード側の再実行だけで解決できると仮定しない。定時実行が連続して欠ける場合は、実行制限、Action状態、スケジューラ遅延、同時実行・キュー詰まりを切り分け、無料範囲内で可能な回避策だけ採用する。
- 全テスト、構文チェック、sanitize、歴史分析、レポート生成、healthcheck、validateを連続した最新コミットで通す。成功したrun IDとコミットSHAを記録する。
